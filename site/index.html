Self-hosted Playwright reporting

Every shard of every run, in one place.

Point your suite at a cameri server and the results land as they happen — live while the build is still going, not a report published at the end. Flake detection, failure clustering and run-over-run history, on infrastructure you own.

Get started View on GitHub
npm install -D @camerihq/playwright-reporter

One container

The API and the dashboard ship in the same image, on the same origin. No proxy.

Nothing leaves

Your traces, videos and test names stay on your infrastructure. No vendor.

Never blocks CI

If cameri is unreachable the reporter shrugs and the tests decide the exit code.

Sharded runs, reassembled

Playwright shards across N machines, so N reporters report into one logical run and none of them knows when the build is done. The server owns that: the first shard to arrive creates the run, the rest join it, and the last one out resolves the status.

The key they agree on comes from the CI build id — never a hostname, pid or timestamp. GitHub Actions, GitLab CI, CircleCI, Buildkite and Jenkins are detected automatically. If a shard dies without reporting, the run is swept to timedOut rather than hanging forever.

The flaky ones, by name

A test that fails and then passes on retry is not a passing test, and a suite-level pass rate will never tell you which one it was. cameri records every attempt, marks the recoveries, and sorts the whole catalogue worst-first.

Failures are clustered by an error signature rather than by message, so the same break across three browsers is one thing to fix, not three.

History that survives a rerun

One bar per day, outcomes stacked inside it, counted per test per run — so a test retried three times is one data point and the flake flag is what says so.

It is the view that answers “has this always been like this, or did we break it on Tuesday”, which is the only question worth asking about a red test.

One comment per merge request

Point a project at a GitLab instance and cameri posts a single comment on the merge request, then rewrites it in place as shards report — a live summary in the thread instead of a note per push.

The access token is encrypted before it is stored and never leaves the server; the dashboard only ever sees a hint of it. Changing that setting needs an admin token, because storing a credential the server will later spend is not something an anonymous visitor gets to do.

Quickstart

Two moving parts: a server you host, and a reporter you add to playwright.config.ts.

  1. Run the server

    One container and one Postgres. DATABASE_URL is the only required variable; the rest have defaults and are documented in the README. 

    services:
  cameri:
    image: ghcr.io/samuelarbibe/cameri:latest
    ports: ["3000:3000"]
    environment:
      DATABASE_URL: postgres://cameri:cameri@postgres:5432/cameri
      PUBLIC_URL: https://cameri.example.com
      CAMERI_ENCRYPTION_KEY: ${CAMERI_ENCRYPTION_KEY:?generate one}
    volumes: ["cameri-storage:/data"]

  2. Create a project

    This prints a record key — what your CI authenticates with. It is shown exactly once, because only its sha256 is stored. 

    docker compose up -d
docker compose exec cameri node dist/bootstrap.js "My App"

  3. Point your suite at it

    Reporting turns itself off when there is no server URL or record key, so the same committed config works on a laptop without a conditional in it. 

    // playwright.config.ts
export default defineConfig({
  reporter: [
    ["list"],
    ["@camerihq/playwright-reporter", { serverUrl: "https://cameri.example.com" }],
  ],
});
    CAMERI_RECORD_KEY=cam_... npx playwright test --shard=1/4

The dashboard is on the same port as the API. Full configuration, storage layout and the upgrade path are in the README.
